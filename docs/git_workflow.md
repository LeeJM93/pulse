# 브랜치·커밋 운영 지침

적용일: 2026-10-03. 사용자가 채택한 Pulse의 기본 작업 정책이다.
[상시 규칙](../AGENTS.md)과 [개발 진행 지침](development.md)에서 이 문서를 읽는다.
기능 요구사항은 [기능명세](../장중_시황_브리핑_프로그램_기능명세.md)를 따른다.

## 1. 저장소와 자동화 범위

Pulse는 기본 로컬 경로 `stock/programs/pulse/`에 있는 독립 Git 저장소다.
상위 `stock/` 저장소와 구분한다. Git 작업 전 현재 작업 폴더의 저장소 루트를 확인한다.
복제본이나 worktree에서는 그 checkout의 루트를 사용하며 기본 로컬 경로로 되돌아가 작업하지 않는다.

사용자가 요청한 구현·수정·문서 변경에는 아래 정책을 적용한다.
조사·설명·읽기 전용 검토만 요청한 경우에는 브랜치나 커밋을 만들지 않는다.

| 작업 | 기본 처리 |
| --- | --- |
| 상태·브랜치·변경 내용 확인 | 직접 수행 |
| 요청한 작업용 로컬 브랜치 생성·재사용 | 직접 수행 |
| 작업 변경 선택·검증·로컬 커밋 | 아래 조건을 충족하면 직접 수행 |
| 원격 생성·변경, push, PR 생성 | 사용자가 해당 작업을 요청했거나 대상과 범위를 사전에 허용한 경우 수행 |
| `main` 병합 | 사용자가 병합까지 요청했거나 사전 병합 정책을 허용한 경우 검증 후 수행 |
| 공유 이력 재작성·강제 push·변경 폐기 | 일반 작업에 포함하지 않는다. 해당 작업과 대상에 대한 명시적 요청이 있어야 한다 |

한 번 허용한 범위는 같은 작업에서 유지한다. 브랜치·커밋마다 반복해서 승인을 요청하지 않는다.
개발을 계속하라는 요청만으로 원격 게시나 `main` 병합까지 허용됐다고 확대하지 않는다.
원격이 없어도 로컬 개발·검증·커밋은 진행할 수 있다. 미설정 상태를 기록하고 원격을 임의로 만들지 않는다.

## 2. 작업 시작 시 확인

1. 저장소 루트, 현재 브랜치 또는 detached HEAD, 시작 커밋을 확인한다. 커밋이 없으면 최초 저장소임을 기록한다.
2. staged·unstaged·untracked 파일을 각각 확인한다. 기존 변경과 이번 작업의 경계를 기록한다.
3. 진행 중인 merge·rebase·cherry-pick과 다른 worktree의 사용 상태를 확인한다. 기존 작업을 임의로 중단하거나 덮어쓰지 않는다.
4. 사용자 요청, [구현·검증 상태](implementation_status.md), 현재 브랜치 목적을 대조한다.
5. 같은 작업용 브랜치이면 이어서 사용한다. 새 작업이면 시작점과 선행 의존성을 확인한 뒤 브랜치를 만든다.

기본 확인 명령의 예는 `git rev-parse --show-toplevel`, `git status --short`, `git branch --show-current`, `git diff`, `git diff --cached`, `git worktree list`다.
Git 실행이나 작성자 설정이 부족하면 성공으로 보고하지 않는다. 작성자 이름·이메일·서명·전역 Git 설정을 임의로 만들거나 바꾸지 않는다.
Git 관련 제약이 있어도 파일을 보존하면서 진행 가능한 구현·문서 작업은 계속하고, 커밋하지 못한 이유를 보고한다.

## 3. 브랜치 운영

- `main`은 검증된 결과를 모으는 기준 브랜치다. 일반 변경은 작업 브랜치에서 수행한다.
- 이름은 `codex/pulse-<짧은-작업명>`을 기본으로 한다. 예: `codex/pulse-bootstrap`, `codex/pulse-futures-sample`, `codex/pulse-fix-time-alignment`.
- 사용자가 지정한 브랜치나 이미 진행 중인 관련 브랜치를 우선한다. 메시지마다 새 브랜치를 만들지 않는다.
- 관련 없는 기능·수정은 나눈다. 큰 Phase는 독립적으로 검토할 수 있는 작업으로 나눌 수 있다.
- 독립 작업은 확인된 `main`에서 시작한다. 원격이 설정돼 있으면 필요한 원격 상태를 확인하고, 확인하지 않은 상태를 최신이라고 보고하지 않는다.
- 선행 작업이 미병합이면 필요한 선행 브랜치의 커밋에서 이어가거나 분기한다. 기반 브랜치·커밋과 의존 관계를 기록하고, 낡은 `main`에서 기능을 중복 구현하지 않는다.
- 저장소 전체를 정리하려고 사용자의 변경을 stash·reset·restore하지 않는다. 다른 작업과 충돌하지 않으면 그대로 보존하고 필요한 범위만 작업한다.
- 분리가 필요하면 관련 지침에 따라 별도 worktree를 검토한다. 기존에 적합한 작업 폴더가 있으면 재사용한다. 저장소 밖의 명세·파일에 의존하지 않게 한다.
- Codex가 만든 worktree의 detached HEAD는 오류로 간주하지 않는다. 시작 커밋과 작업을 보존하고, 이름이 있는 브랜치가 필요한 시점에 그 위치에서 만든다.

### 최초 커밋 예외

아직 커밋이 없는 저장소에서는 명세·상시 규칙·개발 문서·`.gitignore`를 검토해 `main`에 최초 기준 커밋을 만들 수 있다.
이 예외는 개발 기준을 정하는 문서·설정에 한정한다. 프로그램 구현은 이후 작업 브랜치에서 시작한다.
초기 문서 정리 요청에서 이 기준 커밋까지 완료해도 기능 구현을 시작한 것으로 기록하지 않는다.

## 4. 커밋 단위와 검증

하나의 커밋은 한 가지 논리적 변경을 설명할 수 있어야 한다.
동작 변경, 이를 검증하는 테스트, 필요한 문서·설정은 같은 커밋에 포함할 수 있다.
파일별로 기계적으로 나누거나, 서로 무관한 작업을 한 커밋으로 묶지 않는다.

- 의미 있는 구현 단위가 동작하고 검증되면 로컬 커밋한다. 큰 Phase가 끝날 때까지 모든 변경을 쌓아두지 않는다.
- 코드 변경은 구성된 formatter·linter·type checker·관련 테스트를 실행한다. Phase 완료 시 전체 테스트와 해당 demo·통합 실행을 확인한다.
- 문서 변경은 링크·경로·명세와의 일관성을 확인한다. 없는 코드 도구나 테스트를 실행했다고 기록하지 않는다.
- 실제 API·AI·게시·장중 검증이 남았어도 구현과 샘플 검증이 완료된 변경은 커밋할 수 있다. 미검증 항목을 메시지나 상태표에 명시한다.
- 새로 발생한 검사 실패는 수정한 뒤 커밋한다. 환경 제약·기존 실패가 있으면 원인과 영향 범위를 구분하며, 미검증 내용을 정상 통과로 표현하지 않는다.
- 해결되지 않은 실패를 완료 커밋으로 숨기지 않는다. 진행 보존을 위한 미완성 커밋은 별도로 요청받은 경우 그 상태를 명시한다.
- 변경 후 검증 결과가 무효가 됐으면 관련 검증을 다시 수행한다.

Phase 0+1의 예: 개발 도구 구성 → 관측값·정규화·저장 → 지표 계산과 테스트 → 기본 브리핑·웹·demo.
이는 예시이며 구현 의존성에 따라 단위를 조정한다.

## 5. 선택한 변경만 커밋

1. 시작 시 확인한 기존 변경과 비교해 이번 작업의 파일·구간을 식별한다.
2. 경로를 명시하거나 필요한 구간만 staging한다. `git add -A`, `git add .`, `git commit -a`로 전체 변경을 무조건 담지 않는다.
3. 이미 staged 상태였던 사용자 변경도 함께 커밋될 수 있으므로 커밋 직전 index 전체를 검토한다. 자기 파일을 추가한 것만으로 범위가 안전하다고 판단하지 않는다.
4. 다른 사람의 staged 상태를 임의로 해제하지 않는다. 안전하게 분리할 수 없으면 그 커밋만 보류하고 이유를 기록한다. 같은 파일의 겹치는 변경을 작성 주체 확인 없이 가져가지 않는다.
5. 커밋 대상 diff와 `git diff --cached --check`를 확인한다. 비밀값·실행 데이터·불필요한 생성물·관련 없는 변경이 없는지 확인한다.
6. 검증한 코드와 커밋할 코드가 일치하는지 확인한다. 커밋되지 않을 다른 파일이나 변경에 의존해서 테스트만 통과하는 상태를 완료로 처리하지 않는다. 필요한 경우 기존 작업을 건드리지 않는 별도 사본에서 선택한 내용을 검증한다.
7. 커밋 후 ID·요약·포함 파일과 남은 변경을 확인한다. 검사 hook이 실패하면 원인을 해결하며 통과를 위해 `--no-verify`로 우회하지 않는다.

원본 명세·코드·테스트·샘플 fixture·비밀값 없는 설정 예제는 버전 관리한다.
실행 DB·실제 원본 응답·로그·인증정보·로컬 설정·`data/`·`private_runs/`·생성된 `dist/`·작업용 `work/`는 제외한다.
`.gitignore`는 이미 추적 중인 파일을 자동 제거하지 않는다. 기존 추적 파일이 발견되면 영향을 확인해 해당 작업 범위에서 처리한다.
추적 제외가 필요한 파일을 무조건 강제로 추가하거나, 파일을 모두 제외해 샘플 재현에 필요한 fixture까지 빠뜨리지 않는다.

## 6. 커밋 메시지

형식은 `<type>(<scope>): <변경 요약>`을 사용한다. 범위는 필요할 때만 붙인다.
`feat`, `fix`, `docs`, `test`, `refactor`, `build`, `ci`, `chore` 중 실제 변경에 맞는 종류를 선택한다.
요약과 설명은 한국어를 기본으로 하며 API·코드 식별자는 원래 이름을 유지한다.

```text
feat(metrics): 최근 15분 수익률 계산 추가
fix(storage): 기준 시각 이후 관측값 제외
docs(workflow): 브랜치와 커밋 절차 추가
```

본문은 필요한 경우 변경 이유, 관련 FR·AC, 실제 수행한 검증, 남은 외부 검증을 쓴다.
샘플 구현을 실제 연동 성공이라고 표현하지 않는다. `update`, `fix stuff`처럼 내용을 알 수 없는 요약을 피한다.
호환성을 깨는 변경에는 `!` 또는 `BREAKING CHANGE`와 영향·이행 방법을 기록한다.
메시지 형식을 위해 자동 릴리스나 추가 검사 도구를 먼저 설치할 필요는 없다.

## 7. Push·PR·병합과 이력 보존

- 현재 요청이나 사전 허용 범위가 있는 경우에만 대상 원격·브랜치를 확인해 push·PR·병합을 수행한다. 같은 허용 범위의 작업에 재승인을 요구하지 않는다.
- 원격이 없거나 권한이 부족하면 로컬 커밋까지 완료하고 실제 상태를 보고한다. push되지 않은 커밋을 원격 백업됐다고 표현하지 않는다.
- 병합 전 최종 변경과 검증 결과를 확인한다. 원격의 브랜치 보호·필수 검사를 우회하지 않는다.
- 병합 방식을 지정받지 않았다면 유용한 논리적 커밋은 보존하는 일반 merge를 사용한다. 중간 작업을 하나로 합치는 squash는 요청이나 저장소 정책이 있을 때 적용한다.
- 다른 사람이 기반으로 삼을 수 있는 공유 커밋은 임의로 amend·rebase하지 않는다. 보통 수정 커밋을 추가하고, 변경 취소가 필요하면 revert를 우선 검토한다.
- `reset --hard`, `clean -fd`, 강제 push 등 기존 작업을 폐기하거나 공유 이력을 바꾸는 조작은 일상적인 정리 단계로 실행하지 않는다.
- 병합되지 않은 작업 브랜치를 삭제하지 않는다. 정리할 때도 해당 작업 소유의 브랜치인지와 변경 보존 여부를 확인한다.

## 8. 완료 보고와 기록

완료 보고에는 다음을 포함한다.

- 실제 작업 저장소·브랜치와 기반 브랜치/커밋
- 생성한 커밋 ID·요약, 또는 커밋하지 못한 이유
- 수행한 검증과 남은 실제 연동·운영 검증
- 남겨둔 staged·unstaged·untracked 변경과 그 이유
- push·PR·병합의 수행 여부, 관련 의존성과 다음 작업

[구현·검증 상태](implementation_status.md)에 현재 단계와 다음 작업을 남긴다.
문서에 자기 자신을 포함한 커밋의 ID를 억지로 기록해 반복 커밋하지 않는다. 같은 커밋의 실제 ID는 완료 보고에서 전달하고, 이후 기록에서 필요할 때 참조한다.

## 조사 근거

아래 공식 자료를 바탕으로 Pulse의 정책을 정했다. 자동 커밋 범위와 브랜치 이름은 이 프로젝트의 선택이다.

- [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow): 작업 브랜치·검토·병합의 기본 흐름.
- [Git workflows](https://git-scm.com/docs/gitworkflows): 논리적인 변경 단위와 작업 브랜치.
- [Git commit](https://git-scm.com/docs/git-commit), [Git add](https://git-scm.com/docs/git-add): index와 선택한 변경의 커밋.
- [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): 메시지 형식.
- [Codex 변경 검토](https://learn.chatgpt.com/docs/code-review), [Codex worktree](https://learn.chatgpt.com/docs/environments/git-worktrees): 변경 검토 범위와 분리된 작업 폴더.
- [Git ignore](https://git-scm.com/docs/gitignore), [Git revert](https://git-scm.com/docs/git-revert), [Git rebase](https://git-scm.com/book/en/v2/Git-Branching-Rebasing): 추적 제외와 이력 보존.
- [GitHub 브랜치 보호](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [병합 방식](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github).
