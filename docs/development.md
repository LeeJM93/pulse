# 개발 진행 지침

이 문서는 이전 대화의 실행 프롬프트를 파일로 나누어 연결한 진입점이다.
기능 요구사항은 [기능명세 원문](../장중_시황_브리핑_프로그램_기능명세.md)을 따른다.
단계 문서는 구현 순서와 검증 범위를 안내한다. 세부 요구가 충돌하면 명세를 우선하고 문서를 맞춘다.

## 작업 시작

1. [상시 규칙](../AGENTS.md), [Git 운영 지침](git_workflow.md), [구현·검증 상태](implementation_status.md), 현재 코드를 읽는다. 변경 작업이면 저장소·브랜치·기존 변경을 확인하고 관련 작업 브랜치를 재사용하거나 생성한다.
2. 첫 구현 전에는 기능명세 전체를 읽어 범위와 경계를 파악한다. 이후에는 관련 FR·AC와 명세 변경을 확인한다.
3. 아래 표에서 현재 요청과 상태에 맞는 단계 문서를 읽는다. 데이터 연동·정규화 작업에는 [데이터 대응표](data_mapping.md)도 읽는다.
4. 관련 구현·테스트·도구를 확인한 뒤 구현한다. 상태표와 실제 코드가 다르면 근거를 확인해 상태표를 바로잡는다.
5. 구현·검증·자체 변경 검토를 수행하고 상태표와 다음 작업을 갱신한다. 논리적 변경 단위마다 해당 변경만 로컬 커밋하고 남은 변경을 확인한다.

## 단계 선택

- **처음 구현을 시작하는 경우:** Phase 0+1을 선택한다.
- **“계속”, “다음 단계”처럼 단계가 생략된 개발 요청:** 상태표의 진행 중 작업을 먼저 이어간다. 진행 중 작업이 없으면 순서상 첫 미완료 단계 중 선행 조건을 충족하는 단계를 선택한다.
- **특정 기능·수정 요청:** 관련 단계 문서를 읽고 해당 범위만 처리한다. 작은 수정 때문에 이미 검증한 전체 단계를 다시 구현하지 않는다.
- **전체 구현을 요청한 경우:** 요청 범위 안에서 단계별 검증을 마친 뒤 다음 단계로 진행한다. 단계마다 사용자가 프롬프트를 다시 입력하거나 완료 승인을 할 필요는 없다.
- **외부 조건이 부족한 경우:** 가능한 문서 조사·구현·샘플 검증을 마치고, 미설정·권한 부족·제공 불가·미검증을 각각 기록한다. 그 외부 조건에 의존하지 않는 다음 작업은 요청 범위 안에서 진행할 수 있다.
- **문서 작성·검토 요청:** 문서 작업만 수행한다. 이 지침의 존재만으로 구현, 실제 API 호출, 게시 또는 장중 운영을 시작하지 않는다.

별도 단계 지시 없이 “계속”이라고만 한 경우에는 선택한 단계의 구현·검증 결과를 보고하고 다음 작업을 기록한다.
이미 요청한 범위 안의 일반 구현 선택은 직접 결정한다. 새로운 사용자 선택이나 외부 조건이 꼭 필요한 부분만 구체적으로 알린다.
준비되지 않은 외부 연동 때문에 샘플로 개발할 수 있는 AI·일정·웹 기능까지 멈추지 않는다.

## 단계별 작업 문서

| Phase | 작업 문서 | 선행 조건 |
| --- | --- | --- |
| 0+1 | [프로젝트 구성과 현물 샘플](phases/phase-00-01-bootstrap.md) | 없음. 기존 파일과 도구를 먼저 확인한다. |
| 2 | [선물 샘플](phases/phase-02-futures-sample.md) | Phase 0+1의 샘플 실행·저장·기본 브리핑·웹 경로 |
| 3 | [키움 현물 연동](phases/phase-03-spot-api.md) | Phase 0+1의 수집 경계·정규화·저장·품질 처리 |
| 4 | [선물 공급자 연동](phases/phase-04-futures-api.md) | Phase 2의 선물 모델·계산·품질 처리 |
| 5 | [AI 브리핑](phases/phase-05-ai-briefing.md) | Phase 0+1과 Phase 2의 근거 자료·TemplateGenerator. 외부 시장 API 미검증이어도 샘플로 개발할 수 있다. |
| 6 | [일정·중복 방지·복구](phases/phase-06-scheduler.md) | 수집·생성 실행 경계와 상태 저장. 실제 계정 없이 가상 시각과 대역으로 검증할 수 있다. |
| 7 | [정적 사이트 게시](phases/phase-07-publishing.md) | 정적 사이트 생성과 검증된 브리핑·게시 상태 모델 |

선행 조건은 코드와 검증의 실제 의존성이다. 모든 이전 단계의 실제 연동 완료를 일률적으로 요구하지 않는다.
Phase 8의 장중 운영 확인은 실제 거래 세션의 근거가 필요하다.

## 공통 실행 기준

- 실행 디렉터리는 현재 Pulse checkout의 루트다(기본 `stock/programs/pulse/`). 이 디렉터리 아래에 별도의 프로젝트 루트나 `market_briefing/` 프로젝트를 다시 만들지 않는다.
- Python 패키지는 `pulse`, 소스는 `src/pulse/`, 기본 CLI는 `pulse`로 구성한다.
- 문서와 관련 코드를 읽고 기존 유틸리티를 검색한 뒤 현재 요구를 만족하는 가장 작은 변경을 한다.
- 구현 요청에는 계획만 제시하고 끝내지 않는다. 외부 인증 없이 가능한 구현·테스트·샘플 실행을 완료한다.
- P0을 우선한다. P1과 자동 주문·매매 추천 등 범위 밖 기능을 앞당기지 않는다.
- 공급자별 실제 API 필드·단위·기준 시각·집계 범위는 공식 문서와 실제 응답을 확인한다. 문서상 후보를 실제 제공 확인으로 표시하지 않는다.
- 샘플에서 생성·렌더링된 결과는 로컬 검증이다. 원격 게시 확인이나 실제 시장 데이터 연동과 구분한다.
- 시각·오류·재시도·중복 실행은 고정 시각과 샘플·대역으로 재현한다.
- 실행한 명령, 모드, 입력, 예상/실제 결과, 관련 FR·AC, 근거 경로를 기록한다. 기록과 공개 파일에 비밀값을 포함하지 않는다.

## 품질 확인과 종료 기록

코드 변경 후 구성된 formatter·linter·type checker·관련 테스트를 실행한다.
단계를 마칠 때는 전체 테스트와 해당 단계의 demo 또는 통합 실행을 확인한다.
실패를 수정하고 변경 내용을 직접 검토한다. 실제로 수행하지 못한 검증은 이유와 함께 남긴다.
문서만 수정했다면 상대 링크·프로젝트 경로·FR/AC 참조·명세와의 일관성을 확인한다.

Git 절차는 [Git 운영 지침](git_workflow.md)을 따른다. 최초 기준 커밋 이후에는 작업 브랜치에서 변경한다.
커밋할 내용과 검증한 내용이 일치하는지 확인하고, 파일·구간을 선택해 커밋한다.
사용자 변경이나 다른 작업의 staging 상태를 건드리지 않는다. 상태표·문서 변경도 해당 논리적 변경에 포함한다.
Phase 완료와 `main` 병합은 별개다. 병합 권한이 없는 경우 작업 브랜치·커밋과 선행 의존성을 남겨 다음 작업을 이어갈 수 있게 한다.

[구현·검증 상태](implementation_status.md)에 단계와 AC별 근거를 갱신한다.
공급자 확인 내용은 [데이터 대응표](data_mapping.md)에 기록한다.
설치와 실행 방법은 [README](../README.md)에 실제 확인한 명령으로 갱신한다.

보고 순서는 상시 규칙의 `Completed / Verified / Not yet verified / Blocked / Tests / Important decisions / Next`를 따른다.
다음 단계를 판단할 수 있게 남은 작업과 첫 실행 항목을 구체적으로 기록한다.
브랜치·커밋 ID·남은 변경과 push·PR·병합 상태도 함께 보고한다.
